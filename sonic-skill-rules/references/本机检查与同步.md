# 本机技能检查与同步

本文处理本机更新的汇总和上传。用户询问“技能有没有更新”而意图获取远端版本时，转到 [GitHub 更新到本机流程](GitHub更新到本机.md)，不要执行本文默认的上传顺序；其中 OneDrive 定位、扫描及内容比较规则可复用。

## 定位 OneDrive 技能仓库

每次运行检查更新流程时先定位维护源，再扫描技能。相对目录固定为 `AI/skills/sonic`，OneDrive 根路径由当前机器提供。

1. 用户当次明确指定仓库路径时使用该路径；否则读取当前进程的 `OneDrive`、`OneDriveConsumer`、`OneDriveCommercial` 环境变量，忽略空值，用路径连接操作为每个根目录生成 `AI/skills/sonic` 候选，解析为绝对路径并去重。不得修改这些环境变量。
2. 优先选择已经存在的候选目录。候选有多个时，优先使用包含当前这份 `sonic-skill-rules/SKILL.md` 的仓库（解析链接后判断）；其余情况下若有多个不同仓库，列明候选并询问用户选择，不能把个人与企业账户的内容混在一起。
3. 候选均不存在，但只有一个有效且存在的 OneDrive 根目录时，将其下的 `AI/skills/sonic` 作为默认保存位置，在需要保存时创建。只读检测不创建目录。根目录本身不存在时不创建伪 OneDrive 根目录。
4. 无有效环境变量时，可回退到当前技能实际所在的维护仓库，但必须确认它具有 `AI/skills/sonic` 目录结构；报告回退来源。既无有效变量也无已确认仓库时，继续进行可行的只读扫描，说明无法确定保存位置并请求路径，不猜测固定盘符。
5. 后续流程统一使用选定的维护源路径；报告本次实际解析路径。目录位于 OneDrive 下只表示已保存到同步目录，除非有客户端状态证据，不宣称 OneDrive 云端已同步完成。

## 扫描范围

检查下列实际存在的目录，不存在则跳过，不创建空目录。路径中的 `~` 指当前用户目录，环境变量仅在已设置时使用。

- 维护源：上一步从 OneDrive 环境变量定位的 `AI/skills/sonic` 目录。
- Codex 用户目录：`$CODEX_HOME/skills`、`~/.codex/skills`。
- 通用用户目录：`~/.agents/skills`。
- Claude Code 用户目录：`~/.claude/skills`。
- 当前项目根目录和当前工作目录下的 `.agents/skills`、`.codex/skills`、`.claude/skills`，以及用户明确提供的其他技能目录。

只查找这些技能根目录的直接子目录，不全盘递归扫描、不遍历插件缓存或依赖。候选目录必须含 `SKILL.md`。维护源目录由用户明确指定为自建技能目录，其中的技能均纳入，包括尚未带前缀的旧技能；其他目录仅纳入目录名或 frontmatter 的 `name` 以 `sonic-` 开头（忽略大小写）的技能，以及已有明确用户归属证据的自建技能。不能仅因安装在用户目录就认定为用户创建。归属不明的项目列为待确认，不上传第三方或系统技能。新命名仍遵守主规范；旧技能不为同步而改名。

解析目录链接和联接点，以实际路径去重。同名技能有多个独立副本时，先比较内容；完全一致则合并为一个候选，不一致时列出冲突，不凭时间戳或目录优先级选择并覆盖。维护源目录是最终维护位置，但不意味着其中的副本必然最新。

## 比较与判断

默认顺序为：定位 OneDrive 维护源 → 扫描并判断本机副本 → 将可确认的本机新增或更新保存到维护源 → 与 GitHub 比较 → 按本次模式推送或报告差异。访问 GitHub 失败不影响已确认内容保存到 OneDrive 目录；保存成功与 GitHub 同步成功分开报告。

汇总前先比较本机副本。目标不存在时可新增；链接实际指向维护源或内容一致时无需复制。双方内容不同且无法判断更新方向时保留双方并报告冲突，不能以“先保存”为由覆盖已有版本。汇总修改同步补充中文更新日志，并在与 GitHub 比较时包含日志。

1. 通过可用的 GitHub 连接器或 Git 读取 `sonicmingit/sonic-skills` 的实际默认分支和最新提交，确认仓库布局。远端技能按现有路径匹配，首次新增默认放在仓库根目录下的同名技能文件夹。无提交的空仓库按首次发布处理。
2. 比较技能完整文件清单及内容，包含脚本、参考资料、素材和更新日志；不能只比较 `SKILL.md`。可用内容哈希或 Git 差异，忽略文件修改时间及纯文本 CRLF/LF 差异。排除 `.git`、依赖目录、缓存、日志、临时文件、密钥和私人运行数据；已跟踪文件如需排除，报告原因，不静默删除远端文件。技能内部的符号链接应检查实际目标，不上传指向本机其他位置的链接或无关内容。
3. 区分：内容一致、本地新增、本地有可确认更新、仅远端更新、双方冲突、缺少共同基线而无法判断方向。文件时间戳晚不等于内容更新。存在共同提交或可靠同步基线时做三方比较；没有基线且双方内容不同，必须先查看差异和可用历史，不能把“不同”直接当成“本地较新”。仍无法确认时跳过该技能并说明所需信息。
4. 本地缺少某个远端文件或整个技能，不自动解释为用户要删除远端。只有本次修改或历史明确证明有意删除时才纳入删除变更。只在远端存在的技能原样保留。

## 同步可确认的更新

- “检测我创建的 Skill”“检测我创建的技能”以及原有的“检查本机 sonic- 技能并同步”均触发此流程，并按用户已设定的及时同步要求发布本地新增及可确认的本地更新；无须再次逐项请求相同授权。用户说“只检查”或“只检测，不同步”时不发布。
- 用户要求“与 GitHub 对比，不推送”时，默认仍先把确认的本机更新保存到 OneDrive 维护源，再做远端对比，不推送。用户明确说“只检查”“只检测，不同步”或“不修改任何文件”时，整个流程只读，既不汇总写入，也不创建日志或推送。
- 将外部默认目录中确认的新内容汇入维护源目录，保留源文件，处理重复副本后再提交。遇到写入权限限制时按环境机制处理，不偷偷改用过时副本。不要在扫描时自动重建用户的安装链接。
- 按主规范为每个更新的技能补充中文 `CHANGELOG.md`。日志内容依据实际差异；内容未知或存在冲突时不编造日志，不发布该项。
- 检查待发布内容不含凭据或私人运行数据，运行适用的验证，然后仅提交确认的文件。首次发布也必须先完成检查。某个技能阻塞时可先同步其他互不依赖且已确认的技能。
- 优先使用足够完成任务的 GitHub 连接器。通过连接器提交多文件时使用基于最新树的单次提交，并以预期旧提交号更新分支，避免覆盖并发更新；空仓库可通过文件创建接口初始化后继续。使用 Git 时先 fetch，按已确认差异提交并进行普通 push，不强推。
- 推送前远端发生变化时重新比较，不能覆盖新的远端修改。完成后回读分支或提交内容验证；失败保留本地成果并报告未同步项。重跑时内容一致应无新增提交。
