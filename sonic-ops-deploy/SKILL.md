# sonic-ops-规范部署

## 用途与调用

负责将项目部署到 Linux Docker 服务器，也负责整理已有部署的目录结构，以及处理本次变更造成的启动、访问和数据异常。默认实际执行用户授权范围内的操作；用户只要求方案、检查或生成文件时，交付到对应阶段。

示例：
- “按规范部署这个项目。”
- “整理这台服务器上指定应用的目录，保留原有数据和访问方式。”
- “刚整理完应用打不开了，检查并恢复。”

使用当前环境可用的 SSH 工具访问服务器。若当前环境提供服务器列表工具，先列出服务器再选择目标；不猜测机器、地址或凭据。目标无法从上下文确认时询问用户；不要仅为做方案而连接或修改服务器。

## 核心约定

- 新建、可自主命名的项目、仓库和应用目录使用小写英文字母与单个短横线，校验式为 `^[a-z]+(?:-[a-z]+)*$`。普通版本号不进入基础名；第三方名称、镜像标签、语言要求和固定文件名保持原样。
- 每套独立维护的应用使用独立部署目录。未明确指定当前服务器的绝对部署位置时，配置、脚本和目录示例全部使用相对目录，以部署根目录为基准；不默认写死 `/home/docker`。明确指定绝对位置后按该位置落地，项目内部路径仍默认相对。已有部署不因加载本技能自动迁移。
- 开发目录与运行目录分开。按需使用 `app/`、`config/`、`data/`、`logs/`、`backups/`、`scripts/`；多服务在用途目录下按服务名分层。不创建无用空目录，不改写上游内部结构。
- 每套部署根目录必须有 `README.md`。默认使用 `docker-compose.yaml` 和 `docker compose`；选择 CLI 时使用 `docker-run.sh`。只生成实际需要的入口，同时保留两份时标明主方式。
- 所有新建或修改的自定义脚本必须有详细中文注释，顶部说明用途、调用方式、参数及默认行为。`docker-run.sh` 顶部另附注释掉的本项目完整 `docker run` 命令；Compose 配置用中文解释实际参数。
- 自建且从代码仓库部署的项目生成根目录 `deploy.sh`，负责获取目标分支最新代码、判断更新、构建部署和验收。人工执行无更新时询问是否重新部署；Agent 使用显式非交互模式，无论有无更新都执行本次部署，不等待输入。
- 开发阶段已有 `deploy.sh` 时优先复用。代码更新后，将仓库中的脚本同步至部署根目录，核对并调整实例目录及配置，再以部署根目录的 `deploy.sh` 执行部署；保留本地实例设置，避免复制覆盖后丢失配置。
- 部署 README 必须提供带中文用途说明的实际目录层级树，覆盖部署入口、源码或产物、配置、数据和辅助目录；更新目录结构时同步维护。
- 所有自定义部署脚本根据自身位置定位部署根目录，根目录入口使用自身目录，`scripts/` 内辅助脚本定位父目录；源码、产物、配置、数据、日志、备份和 Compose 文件默认使用相对路径。容器目标路径遵循镜像要求的绝对路径，设备等系统固定路径作为例外记录；工具必要时可从脚本位置动态解析绝对路径，不硬编码服务器位置。
- 保留业务数据、实际配置和凭据。源码库保存部署模板及 `.env.example`，不提交真实 `.env`、运行数据或备份。不要在报告中输出凭据。
- `application.yaml` 等实际实例配置首次部署时从默认模板初始化到 `./config/`，之后持久保留；更新代码时比较旧模板、新模板和实际配置，保留定制值并处理新版配置变化，不每次重新覆盖。支持外部覆盖配置时优先只维护实例差异，实际加载方式按项目核实。
- 目录整理默认保留镜像版本、访问入口和资源身份，不顺带升级程序或数据库。确有必要的关联修改应说明并记录。

细节见 [目录与配置规则](references/directory-rules.md)。实施整理、更新或故障恢复前，读取 [迁移与恢复](references/migration-recovery.md)。

生成脚本、Compose 或源码一键部署入口时，读取 [脚本注释与一键部署规则](references/script-rules.md)。

## 执行流程

### 1. 确定目标与现状

明确任务属于首次部署、更新、目录整理或故障恢复，核对服务器和应用范围。检查实际 Docker/Compose 版本、资源与磁盘空间，以及现有入口、容器、镜像、挂载、卷、网络、端口、权限和访问路径。

已有应用先建立运行基线：容器与健康状态、近期日志、页面/API 或实际核心操作是否正常。原有故障单独记录，避免把“进程原本就在运行”当作业务正常。

### 2. 准备可执行变更

首次部署按上游文档确认镜像、架构、配置、持久化位置和初始化要求，不直接套用示例容器路径。

更新或整理先建立旧位置到新位置的映射，标明停机步骤、备份、切换方式、验收标准和失败恢复顺序。迁移记录存放在本次整理不会覆盖的位置，保证中断后仍能找到。

已获授权的部署或整理继续执行必要步骤，无须每一步重复确认。遇到目标不明、需删除唯一数据副本、无法保留恢复路径，或影响用户未授权的其他应用时，先完成可做的检查，再说明具体问题并询问。不得把“整理目录”扩大为整机清理。

### 3. 备份并实施

已有数据按应用支持的方式生成一致性备份，检查备份产物、可读性和恢复所需材料。明确哪些已验证、哪些尚未做恢复演练；运行中直接复制数据库目录不能默认算有效备份。

生成和校验配置、准备真实挂载来源及权限后，再进行创建、更新或停写切换。目录整理逐个应用完成；有共享依赖时按依赖安排，不并行切换共同写入同一数据的实例。

### 4. 验收

配置校验只是预检查。实施后检查容器、健康状态、日志、访问入口、核心功能、持久数据与权限；有反向代理或定时任务时检查相关引用。需要写入测试时采用可清理的最小操作，不改动真实业务记录。

只报告实际执行的验证。容器运行、HTTP 返回或重启成功中的任意单项，均不能单独证明全部业务正常。缺少访问条件时说明尚未验证的部分。

### 5. 失败处理与交付

本次变更造成异常时，继续排错并恢复，不在“已整理文件”时结束任务。保存必要证据后判断能否作小范围修复；否则执行已准备的回滚，回滚后重复业务验收。

若恢复仍失败，保留新旧数据和配置，停止扩大变更，报告故障、已尝试操作、当前可用性及下一步缺失条件。只有通过恢复验证，才报告“已恢复”。

交付更新后的部署 README、实际目录和管理方式、部署版本、验证结果、备份位置、变更记录，以及保留的旧副本和后续处理条件。保留旧副本不等于重复启动旧实例。清理旧数据或备份属于单独的清理范围，不能作为目录整理的默认收尾。
