# 脚本注释与一键部署规则

## 所有脚本的中文说明

所有新建或修改的自定义部署、备份、恢复及其他辅助脚本，必须写详细中文注释。说明关键步骤的目的、前置条件、失败处理和数据影响；函数、重要变量及不直观的命令应有解释，不仅逐字翻译命令。调用第三方脚本不要求改写上游文件。

脚本顶部在 shebang 之后、执行逻辑之前说明：
- 脚本用途、适用应用、依赖、执行位置和所需权限。
- 人工调用与 Agent 调用示例。
- 每个命令行参数的意义、取值、默认值、能否组合，以及无参数行为；没有参数时明确写出。
- 用户可调整的配置变量或环境变量及优先级，不把脚本参数与 Docker 参数混为一谈。
- 会修改哪些资源、是否重建或停机、持久化数据如何保留、失败后如何恢复。

提供中文 `--help`，与顶部说明一致；未知参数、缺失值和冲突组合明确报错。实际状态、取消、成功与失败提示使用中文；失败返回非零退出码。

## docker-run.sh 顶部参考命令

在顶部说明区写出本项目完整的 `docker run` 命令，每行使用 `#` 注释，仅供阅读，不执行。包含实际使用的镜像、容器名、端口、挂载、环境文件、网络和重启策略；没有使用的选项不凑入示例。

说明每个选项的用途和本项目实际含义，例如哪个端口用于访问、哪个挂载必须保留、配置为何只读。命令中的密码等用环境文件或安全引用表示，不把真实凭据写进注释。

示意格式如下，生成项目脚本时必须换成本项目真实配置；此处示意值不能直接交付为已完成部署脚本：

```bash
#!/usr/bin/env bash
# 用途、依赖、调用示例、脚本参数与默认行为在这里逐项说明。
# 参考命令：以下仅供阅读，不参与执行；与脚本实际启动参数保持一致。
# docker run --detach \
#   --name sonic-notes-app \
#   --restart unless-stopped \
#   --env-file ./.env \
#   --mount type=bind,src=./data,dst=/app/data \
#   your-registry/your-image:version
# --detach：在后台运行容器。
# --name：指定本实例容器名，供状态检查及后续管理使用。
# --restart：除人工停止等情况外，按该策略重新启动容器。
# --env-file：从实例环境文件读取应用需要的变量，文件不入库。
# --mount：将宿主持久数据挂入镜像要求的位置，更新时保留来源数据。
# 最后一项：本项目采用的镜像及明确版本，更新时与实际执行命令一起维护。
```

参考命令和执行逻辑必须同时更新。带可选参数时，说明参考命令对应的默认值或示例组合，以及变化项如何展开。`docker-run.sh` 负责容器运行；`deploy.sh` 负责仓库更新和整套部署编排，两者职责不重复。

## Compose 中文备注

在 `docker-compose.yaml` 中为实际配置项添加中文注释，解释意义及取值理由。重复服务可在共享定义处解释通用项，各服务补充差异。

重点说明项目名、服务用途、镜像版本或构建上下文、端口的宿主与容器对应关系、环境变量来源、持久化挂载、只读属性、目录预创建要求、网络、健康检查、依赖就绪和重启策略。只解释配置中实际存在的项；不为增加备注而添加无用参数。

## 自建源码项目的一键部署

为用户自行维护、从 Git 源码部署的项目提供部署根目录 `deploy.sh`。开发阶段已经在仓库根目录或 `deploy/` 中维护该脚本时，优先复用并明确唯一来源路径，不另造一份功能重复的脚本。仅运行上游成品镜像的应用不强行创建 Git 更新流程；其更新方式写入 README。

### 从开发仓库同步到部署根目录

代码更新后，先核对仓库脚本变化，将指定来源的 `deploy.sh` 复制到部署根目录，检查语法及配置，再调用部署根目录的脚本。既支持 Agent 完成同步后执行，也支持根目录入口自行获取代码、同步新版并有控制地重新进入新版脚本。

同步前保留原入口及实例设置。通用脚本与实例配置优先分离，例如实例目录参数放在 `./config/deploy.env` 中，复制新版脚本后继续加载；如果项目在脚本顶部直接维护参数，则先记录本地值，更新后逐项合入，不能机械覆盖或直接保留旧脚本而遗漏新版逻辑。路径、变量格式和是否加载配置由项目明确约定，配置文件不能误作容器环境文件。

实例路径默认采用 `./app/source`、`./app/dist`、`./config`、`./data` 和 `./docker-compose.yaml` 等相对值，统一以部署根目录为基准。仓库中的脚本需要适配复制后的根目录布局；首次复制、更新同步、实例配置调整及运行命令都写入 README。

复制前检查脚本依赖的辅助脚本、模板和配置示例。需要时按明确清单同步成套依赖并保留实例值，不能只复制入口却遗漏相对引用文件。同步 Compose 时重新核对复制后的路径基准；依赖均固定到本次选定提交，不从变化中的分支反复取不同版本。

顶部配置明确代码仓库、远端、目标分支、源码目录、构建方式、部署入口和验收方式。默认分支以用户选择或已核实的仓库设置为准，不猜测固定为 main。源码默认放在 `app/source/`，不要直接克隆到含运行数据的应用根目录并覆盖现有文件。

明确采用 Docker 内编译还是宿主机先编译：前者将真实源码目录作为构建上下文，通过 Dockerfile 生成镜像；后者运行项目构建命令，按需将发布产物整理到 `app/dist/`，再打包镜像或挂载发布目录。实际 Compose 入口留在应用根目录，由 `deploy.sh` 串联源码更新、构建、部署及验收。具体路径规则见 [Git 源码与编译产物](directory-rules.md#git-源码与编译产物)。

### 人工与 Agent 调用

| 调用方式 | 有更新 | 无更新 |
|---|---|---|
| `bash ./deploy.sh` | 更新源码后直接构建部署 | 提示“当前没有更新，是否重新部署？[y/N]”，用户同意才部署 |
| `bash ./deploy.sh --non-interactive` | 更新源码后直接构建部署 | 直接构建部署，不询问 |
| `bash ./deploy.sh --help` | 显示中文帮助，不获取代码或部署 | 同左 |

人工确认默认否，输入 `y` 或 `yes` 同意；拒绝或输入结束时取消重部署并明确提示。人工模式没有可读终端时不等待输入，提示使用非交互参数后结束。Agent 必须显式使用 `--non-interactive`，不能靠猜测调用者身份或模拟输入跳过提示。

非交互只控制无更新时是否询问，不跳过前置检查、备份、验证和错误处理，也不扩大本次部署授权范围。

### 更新判断与执行顺序

部署前按 [默认模板与实例配置更新](directory-rules.md#默认模板与实例配置更新) 检查 `application.yaml` 等配置变化。首次初始化实际配置；后续保留实例文件并生成候选更新，不把源码模板直接覆盖到 `config/`。无法自动处理的配置迁移在切换服务前报错；Agent 可按已知项目规则处理，缺少必要实例值时再询问。

1. 先取得同一应用的部署锁，再检查依赖、配置、仓库身份、分支与源码工作区。检测到未提交修改或目标异常时停止并说明，不自动丢弃修改、强制 reset、切分支或 stash。构建生成物按项目规则忽略或在独立目录构建，不用批量清理工作区规避检查。任何脚本、模板或实例配置被替换前，保存旧入口及成套依赖、原实际配置、旧模板基线和实际运行的镜像或产物身份。
2. 获取指定远端和分支的最新状态，再比较提交；确认分叉或本地领先于本轮获取的目标远端时停止并说明，不依据过期远端记录作判断。网络、认证或 fetch 失败返回错误，不提示“当前没有更新”。首次部署缺少源码时按已核实地址克隆，视为需要部署；目标目录非空且不是对应仓库时先核对归属，不覆盖克隆。
3. 远端有可快进的新提交时使用快进方式更新并固定本轮目标提交。同步根目录脚本及必要依赖、保留并调整实例配置，再进入部署阶段；若当前脚本负责自身更新，按下文受控重入规则处理。当前源码与远端一致时，还需比较最后成功部署提交：上次部署失败、成功记录缺失或当前代码尚未成功部署，都视为需要部署，不能仅因 Git 工作区已最新而跳过。
4. 人工模式“当前没有更新”仅指目标分支代码和成功部署提交一致，同时提示本地配置仍可能已变化，用户可选择重新部署使配置生效；Agent 模式直接部署。首次部署、待完成的失败部署按需要部署处理。更新判断不暗指配置、外部依赖或可变镜像标签均未变化。
5. 使用变更前已保存的版本及配置记录，准备本项目所需一致性数据备份，构建新产物或镜像并校验候选配置；备份完成后仍有写入时，按停写切换方案处理恢复点。候选配置在实际切换前不覆盖生效配置。尽量在停止旧服务前完成可提前进行的构建。自建镜像使用可关联源码提交的版本，保证原版本可用于恢复；同一提交重新构建时仍记录实际镜像身份并保留旧镜像，不能仅靠被覆盖的标签回滚。
6. 按项目实际方式重新部署。无代码变化但用户或 Agent 已要求重部署时，必须执行有效的构建及重建流程，不能只启动旧容器就声称重部署完成；保留业务数据，避免顺带重建无须变更的数据库等依赖。
7. 部署后执行健康与业务验收，仅成功后写入部署状态。状态至少记录源码提交、镜像或发布产物身份和时间，保存在源码工作区外，例如 `config/deploy-state/`；失败不得更新成功标记。
8. 失败保留错误信息，按 [迁移与恢复](migration-recovery.md) 修复或回滚。脚本仅在具备已核实的恢复步骤时自动恢复，不把恢复源码提交等同于恢复业务；有数据结构变化时遵守兼容性要求。

构建失败且尚未切换服务时保持旧服务不变；已切换后验收失败才按恢复步骤处理。健康及业务验证设置明确超时和有限重试，超过上限进入失败处理，不能无限等待。一键脚本遇到失败应非零退出；即使成功回滚，也报告“本次部署失败、已恢复旧版”，不能返回本次部署成功。

首次部署没有旧版本时，失败应报告“首次部署未完成”，保留初始化数据及排错材料，不声称已回滚。取消或中断时记录已完成阶段，释放自身持有的锁并保留恢复材料；后续调用先核对实际状态，不能因存在成功历史就忽略未完成切换。

部署状态更新应在锁内原子写入，并保留上次成功版本及本次失败或回滚结果。回滚后状态必须对应实际恢复的镜像、配置和产物；不得把尝试部署的提交写成已成功版本。

一键脚本应防止同一应用并发部署；记录每次部署结果且不泄露凭据。不得在正在读取执行的脚本上直接覆盖写入：先把新版复制至临时文件、完成语法和配置检查，再替换根目录入口。当前执行先固定自身版本；需要本轮采用新版时，有控制地重新进入根目录新版入口，并保留调用模式、参数及部署锁的连续性。标记本轮已同步阶段，避免反复获取、复制或无限重入；不得混用新旧版本的脚本依赖。进入新版失败时恢复原入口并报错。

若当前执行版本通过临时快照固定，必须保留进入快照前解析的部署根目录，不能将临时快照所在目录误作项目根目录。自更新过程中仅准备候选实例配置，明确进入新版成功后的应用阶段，避免启动新版失败却留下不匹配的配置。

### 交付验证

结合实际项目验证：人工有更新自动部署、无更新拒绝与同意、非交互无更新直接部署、获取代码失败、本地修改或本地领先、上次部署失败后的重试，以及部署失败和回滚后的退出状态。另检查从其他目录调用、脚本复制后的辅助依赖、实例配置保留、Compose 解析路径，以及并发拒绝和自更新仅进入新版一次。首次或修改脚本先完成可用的语法检查，行为检查使用隔离仓库或模拟部署，不能为测试擅自重部署生产项目。
