# 已有部署整理、更新与故障恢复

## 变更前记录

建立可恢复的变更记录，至少包含：
- 服务器与目标应用、原本是否正常、关键访问与功能检查结果。
- 原目录和目标目录、当前入口及其调用目录、Compose 实际项目名与服务名。
- 容器及镜像身份、版本或摘要、启动参数、端口与网络。
- 所有持久化挂载、命名卷、配置与环境文件位置，以及必要 UID/GID。
- 反向代理、定时任务、systemd、脚本及其他应用的路径或资源引用。
- 备份产物、完整性检查、切换步骤、失败恢复顺序和恢复验收条件。

原始配置及可能含凭据的检查结果存放在服务器受限目录，报告只给出脱敏摘要。不能把原始 `docker inspect` 或 `.env` 直接发到公开记录。

## 整理顺序

1. 检查目标目录重名、磁盘容量和所需权限，列出每个路径的迁移关系。配置路径变更与程序升级分开实施。
2. 保存原配置与实例身份；按上游要求生成一致性备份。记录备份时间及之后可能新增的数据。
3. 大数据可先预复制缩短停机，但正式切换前停止应用及其他写入者，再完成最终同步。保留权限、所有者、符号链接等应用所需属性；不要在源仍写入时宣称复制完整。
4. 按映射准备新目录和配置，核对相对路径、命名卷及网络实际指向。禁止直接在无关容器仍使用的共享路径上移动或改权限。
5. 校验配置后切换运行入口，确保旧实例不会被重启策略、守护服务或定时任务再次拉起并并发写数据。停机用不会删除持久数据的方式；不使用 `down -v` 或批量 prune 完成普通整理。
6. 启动并验收容器、应用入口、关键功能和持久数据；检查代理、定时任务和外部依赖。
7. 更新部署 README 与模板，记录旧位置保留情况。未完成验收不删除旧副本，不将临时兼容链接视为迁移已全部完成。

如果任务中断，先重新检查实际容器、写入者及新旧数据状态，从记录确定已完成阶段；不要盲目重跑整段迁移命令。

目录整理使用本次变更前已记录的程序版本和配置，不调用会自动拉取最新代码的更新流程。需要复用 `deploy.sh` 时，先确认它支持固定既有版本的整理或恢复模式；不支持时按已核实的 Compose/CLI 入口切换原版本，避免整理过程中意外升级。

## 变更后故障处理

用户说“整理完崩了”“启动不了”“数据不见了”时，优先恢复业务。先确认故障是否与本次变更相关，保存必要日志和配置差异，暂停后续整理。

重点检查：
- 相对路径基准变化、挂错目录、空目录遮蔽镜像文件、配置缺失或挂载类型错误。
- UID/GID 与权限、只读配置、系统安全标签等实际环境限制。
- Compose 项目名变化引起的新卷或新网络、原卷未挂载、数据库未就绪。
- 端口冲突、代理或脚本仍引用旧路径、环境文件未加载或插值变化。
- 迁移复制不完整、遗漏写入者、同时启动两套实例、程序与数据版本不兼容。

### 修复或回滚

故障已定位且能在本次变更范围内作明确的小修复时，修复后立即验证。重复出现同类失败或原因不明时，停止盲目重建，使用预备的恢复路径；不反复重启掩盖问题，不先删除疑似异常数据。

回滚前先判断新位置是否已接收业务写入。存在新写入时，停止所有相关写入者，保存新旧数据，选择可保持一致性的恢复或数据合并方案。不能直接切回旧副本而静默丢掉新数据；无法确认方案时，保留现场并说明需要的判断。

仅移动目录且数据格式未改变时，恢复原入口、配置、挂载和必要资源身份，并使用经确认的当前完整数据。涉及程序升级或数据库结构迁移时，确认旧版兼容性；旧镜像不兼容新数据时，按备份恢复方法恢复匹配的数据，说明恢复点及可能损失的时间范围。

回滚同样需要检查容器、日志、访问、关键功能和数据。分别报告“恢复操作已执行”和“业务已验证恢复”，不混为一谈。恢复受阻时明确最后已知正常版本、当前服务状态、数据副本位置及阻塞条件。
