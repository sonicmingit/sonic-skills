# 目录与配置规则

## 命名与开发目录

仓库、源码目录和正式部署目录使用稳定基础名，例如 `sonic-notes`。独立组件仓库可用 `sonic-notes-api`；同仓库内可用 `api/`、`web/`，也可以遵循框架原有 `src/` 结构。

自定义多词脚本使用短横线，例如 `backup-data.sh`。保留 `Dockerfile`、`README.md`、`.env`、`package.json`、`__init__.py` 等固定文件名；Python 包按语言规则命名。已被其他工具引用的旧脚本名允许保留并记录例外。

“仅小写字母与短横线”约束项目基础名和自主命名的业务目录，不约束用于恢复定位的时间戳备份、提交摘要、发布版本等机器生成标识；版本产物目录可以包含数字，并在 README 标明用途，不因此把版本号加入项目基础名。

开发根目录沿用用户位置，不强制迁移。仓库 `deploy/` 保存可复用部署配置、脚本和 `.env.example`；运行数据、备份、日志和真实凭据不进入源码仓库。生产通用配置变更同步回模板，环境专用值留在实例配置中。

## 部署结构

未明确指定当前服务器的 Docker 绝对部署位置时，使用 `./<应用名>/` 表示应用目录、使用 `./` 表示已进入的部署根目录，不假设 `/home/docker`。首次生成文件可先交付相对目录结构；真正落地执行前从用户指定位置或已核实的目标工作目录确定实际位置，不自行猜测。已明确绝对位置时可在部署记录中写出真实位置，内部配置仍使用相对路径。

以下为可选路径清单，不要求全部创建：

| 路径 | 用途 |
|---|---|
| `docker-compose.yaml` | 采用 Compose 时的部署入口 |
| `docker-run.sh` | 采用 CLI 时的启动入口 |
| `deploy.sh` | 自建源码项目的一键拉取、更新判断、构建部署和验收入口 |
| `README.md` | 必需的实际部署说明 |
| `.env`、`.env.example` | 实际参数与无凭据的参数示例，按需提供 |
| `app/` | 发布产物、静态文件或构建上下文；程序在镜像中时可省略 |
| `config/` | 宿主维护的配置 |
| `data/` | 持久业务数据 |
| `logs/` | 应用主动写出的文件日志 |
| `backups/` | 本地备份导出；重要副本另存独立位置 |
| `scripts/` | 备份、恢复等辅助脚本 |

多服务使用 `config/nginx/`、`data/postgres/` 等用途加服务名结构。宿主目录统一不要求容器内目录同名。不得把空宿主目录挂到镜像程序目录而遮蔽原文件。

## Git 源码与编译产物

从 GitHub 或其他 Git 仓库拉取、用于本机编译部署的完整源码，默认放在应用目录的 `app/source/`，保留 `.git/` 和上游内部结构。实际 Compose 启动入口放在应用根目录，构建路径指向真实源码或产物位置。

| 构建方式 | 源码与产物安排 | Compose 启动方式 |
|---|---|---|
| Docker 内编译 | 源码放 `app/source/`，由项目 Dockerfile 编译并生成镜像；不必创建宿主 `app/dist/` | 构建上下文按实际配置指向 `./app/source` 或所需子目录，然后使用构建镜像启动 |
| 宿主机先编译 | 在 `app/source/` 执行项目构建；按需将发布结果整理到 `app/dist/`，不强改上游构建输出结构 | 将产物打包进镜像，或按应用要求将发布目录挂载到容器后启动 |

`app/dist/` 仅在实际需要独立发布产物时创建。README 记录真实构建命令、源码及输出路径、Dockerfile 和构建上下文。`deploy.sh` 串联获取源码、判断更新、编译或构建镜像、Compose 部署及验收。

源码更新仅操作源码工作区，不覆盖部署根目录的实际配置、环境文件与业务数据。运行配置放 `config/`、业务数据放 `data/`，不得把这些内容混入会随源码更新或构建被清理的目录。已有项目使用不同位置时，先检查依赖，再按迁移流程整理。

宿主机编译时先写入独立暂存目录或版本目录，不直接清空或覆盖运行容器正在挂载的 `app/dist/`，也不在正在被容器当作运行代码使用的源码目录中直接更新。构建成功后保留旧产物，按应用支持的方式停机切换或切换发布版本并重新创建相关容器；不要假设改动宿主符号链接会自动切换已有容器挂载。失败时能重新指向旧产物并验证恢复。

应用部署根目录不等同于 Docker 引擎的数据根目录。优先采用上游支持的绑定挂载；必须保留的命名卷记录真实卷名、用途与备份方式，不为目录统一直接转换卷类型。不要迁移 Docker 引擎目录来完成普通应用整理。

## 默认模板与实例配置更新

`application.yaml` 等配置分成仓库默认模板与服务器实际实例配置两部分。仓库文件保持上游默认或无凭据示例，不直接在已跟踪源码文件中写入生产参数；实际配置默认持久保存在 `./config/<服务名>/`，单服务也可用 `./config/application.yaml`。首次初始化后不在每次部署时重新移出或覆盖。

优先使用应用明确支持的外部配置或覆盖配置机制：仓库默认值随程序更新，外部文件只维护本实例差异。若应用仅支持完整配置文件，则从模板初始化独立实际文件并维护完整内容。通过启动参数、环境变量或挂载显式加载，按项目版本核实文件位置、优先级及列表覆盖行为；文件放进 `config/` 不代表自动生效。不得将真实生产配置复制进源码仓库或镜像构建上下文。

更新前保留旧版本默认模板、原实际配置及其对应版本；对照新版本模板生成候选配置：

| 变化情况 | 处理方式 |
|---|---|
| 用户定制值，新版含义未变 | 保留用户值，例如数据库地址、端口与存储位置 |
| 原来沿用默认值，新版调整默认值 | 核对兼容性及部署影响后按新版规则更新，不盲目把所有旧值固定下来 |
| 新版新增配置 | 按文档判断是否必填、能否使用默认值；需实例专用值时补齐，不猜测密码或地址 |
| 配置项删除、改名、类型或含义变化 | 按迁移说明调整；不能仅按同名键覆盖，或无条件保留失效项 |
| 双方修改同一项，或列表、多文档等结构无法可靠合并 | 列出具体冲突及影响，Agent 根据已知意图处理；仍缺少必要选择时停止切换并询问 |

不能仅以“新模板为底，旧值全部覆盖”实现通用 YAML 合并，也不能使用文本替换处理结构变更。涉及格式重写时尽量保留中文注释，检查重复键、类型、占位值和应用实际支持的语义。缺少旧模板基线时不猜测哪些是用户定制：先保留原文件，结合版本历史和项目文档判断，并记录未确定项。

候选配置校验通过后再应用；会被运行应用热加载的配置尤其不能提前覆盖。切换时遵循项目重载或容器重建方式，检查实际配置生效和业务结果；失败时恢复匹配的配置与程序版本。`--non-interactive` 不授权盲目解决未知配置冲突，自动化脚本遇到无法处理的迁移应保留旧服务并非零退出。

部署成功后保存新的默认模板基线和实际配置版本关联，供下次比较；失败不推进成功基线。备份及可能含凭据的差异仅保留在受限位置，报告使用脱敏摘要。

## 路径与启动细则

- 源码、构建产物、配置、数据、日志、备份、环境文件、脚本引用及 Compose 文件路径全部默认相对配置。所有自定义部署脚本先定位其自身所在的部署根目录；辅助脚本在 `scripts/` 内时根据自身位置定位父目录，不能误将 `scripts/` 作为部署根目录。
- 复制到部署根目录的脚本按根目录布局解析路径，不能继续假设位于仓库根目录或 `deploy/`。例如源码为 `./app/source`、产物为 `./app/dist`、Compose 为 `./docker-compose.yaml`。已有不同布局先核对后调整。
- 相对路径要求针对宿主可控的业务路径。容器目标、系统设备等上游要求的绝对路径保留；工具执行时必须绝对路径的，从已定位的部署根目录动态展开，并在中文注释中说明。
- Compose 显式设置稳定的顶层 `name`，已有部署先核对当前项目身份。`-p`、`COMPOSE_PROJECT_NAME` 等覆盖项记录在 README。
- 默认由 Compose 生成容器名。多环境分别隔离实例名、数据路径和宿主端口；共享依赖必须明确记录。
- 单文件 Compose 相对路径以配置文件目录为基准；多文件、项目目录覆盖等情况先检查实际解析结果。配置校验避免将含凭据的完整展开结果输出到聊天或公开日志。
- 仓库 Compose 模板复制到部署根目录后，重新核对 `build.context`、`dockerfile`、挂载、环境文件及脚本引用。构建上下文相对 Compose 文件定位，`dockerfile` 相对构建上下文定位，不能把两者当成同一基准。主配置、覆盖文件与实例参数记录来源及同步方式，不直接用仓库默认值覆盖生产设置。
- 需要 Compose 插值的环境文件显式约定位置，必要时通过 `--env-file` 指定；Shell 已导出的同名变量可能覆盖文件值，应核对并处理实际冲突，不静默部署到错误项目或使用错误镜像。脚本读取的实例设置不会天然成为 Compose 插值变量，需按格式明确传递；容器 `env_file` 另行配置。
- 绑定挂载优先使用长语法和 `bind.create_host_path: false`。启动前创建真实数据目录或配置文件；配置只读与否按应用要求确定。
- 部署在目标服务器执行。远程 Docker context 不会自动把本地文件上传到服务器。
- CLI 脚本使用 Bash、UTF-8、LF 换行，并先执行以下定位逻辑。需要兼容不同 Docker 版本时，绑定来源由 `"$app_dir/data"` 等动态绝对路径生成，不硬编码服务器位置。

```bash
#!/usr/bin/env bash
set -euo pipefail
app_dir="$(cd -- "$(dirname -- "${BASH_SOURCE[0]}")" && pwd -P)"
cd -- "$app_dir"
```

- CLI 创建容器前先确认 Docker 可访问。已有同名容器时检查所属项目及状态；运行中的容器不代表新配置已生效，停止的容器也不自动视为部署成功。启动原容器、重建和更新按实际任务区分，不默认删除容器。
- `.env` 的 Compose 插值与容器环境注入分开处理。只向相应服务传递需要的变量；CLI 与 Compose 共用文件时使用两者均支持的简单实值格式，注意引号和插值语义差异。
- 镜像记录可识别版本或摘要。未知镜像路径、配置、端口不得凭模板猜测。数据库依赖就绪按应用需求配置健康检查及启动条件。
- 权限按实际 UID/GID 设置，不统一 `chmod 777`。标准输出由 Docker 日志机制管理，按应用配置保留策略；`logs/` 不会自动收集标准输出。

## 项目说明

按 [部署 README 模板](../assets/deployment-readme.md) 填写实际值。不适用栏目注明原因，不保留会被误执行的占位命令。README 不保存密码、令牌或含凭据的完整连接串。

必须提供与项目实际一致的 `tree` 风格目录层级说明，每项附中文用途，标出源码、镜像构建上下文、部署入口、持久化数据和恢复材料。仅展示相关层级，不展开 `.git/`、依赖缓存或海量业务数据；省略部分明确标记。命名卷和部署根目录外的依赖另行说明，不能伪装为目录树内的真实文件夹。示例结构不要求创建全部目录。
