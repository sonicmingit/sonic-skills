# 内置 Code Review 流程

## 启动条件
仅在用户明确要求本次 Code Review，或回答开发完成后的询问为“需要”时执行。先确认范围：工作区、指定提交区间、分支或 PR。授权审查不等于授权修改代码、发布 PR 评论、合并或部署。

## 执行方法
1. 重新读取需求和验收条件，暂停编辑，以实际差异判断行为，不以开发时的推理作为正确性证据。
2. 用 `git status --short` 确认范围。工作区检查 `git diff`、`git diff --cached` 以及相关未跟踪文件；提交区间按用户指定基线比较，分支审查确认目标分支与 merge-base。范围为空且未指定文件时先澄清，不自行选全仓审查。
3. 阅读变更文件完整相关逻辑、调用者、被调用组件、测试和接口契约。查阅本地阿里手册涉及章节。把既有缺陷与本次引入、暴露或放大的问题分开，不扩成无关重构。
4. 沿正常、边界、失败和并发路径检查业务行为。重点核对重复功能与提取位置、中文注释、分层依赖、事务代理及回滚、锁和线程池、鉴权与数据归属、SQL 与迁移、超时重试和幂等、资源释放、敏感日志及契约兼容。针对整个变更范围检查复用和一致性，不能只搜索几个猜测的符号便宣称覆盖完整。
5. 核对已有构建与测试结果；必要时执行范围内、无外部破坏性副作用的检查。未执行或依赖真实设备、生产数据的验证单列缺口，不把缺少外部证据直接当成已证实代码缺陷。
6. 输出中文报告，不在审查阶段修改代码。修复按用户已授权范围进入独立开发阶段；修复高风险问题后核查受影响路径。不得自动发表评论、合并或部署。

## 严重程度与证据
- P0：可导致严重泄露、广泛服务不可用或不可恢复数据损失的紧急问题。
- P1：影响主要业务、权限隔离、数据正确性或发布可用性的缺陷，建议发布前修复。
- P2：有可复现影响的一般功能、维护或性能问题。
- P3：非阻塞改进；个人偏好不冒充缺陷。

每条问题包含文件与行号、触发条件、具体影响、判断依据和修复建议；高风险项附可行的最小修改示意及验证办法。不能确定时说明假设与待核验事实，不编造复现结果。未解决 P0/P1 不给出通过结论，也不按问题数量稀释风险。

报告包含：范围与基线、按严重程度排序的问题、执行过的验证与缺口、总体结论及建议。不发现问题时表述为“本次范围内未发现可证实缺陷”，不能保证没有缺陷；测试通过也不等于已做审查。

## 模型选择
只选择宿主实际提供且获授权使用的模型。局部简单变更使用能够理解调用链的代码模型；事务、权限、并发、跨服务一致性或数据迁移优先更强推理能力。无法切换时使用当前模型并说明限制，不能声称调用了未使用的模型。独立评审和模型切换遵循 [技能正文的交接与分工规则](../SKILL.md)。其他宿主由用户选择审查安排。模型信息仅可出现在工作报告，不写入产品代码、注释或业务日志。
