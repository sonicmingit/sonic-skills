# sonic-dev-Java开发规范

调用示例：“使用 $sonic-dev-Java开发规范 开发这个接口，并完成 Code Review。”

## 基线与接手

以阿里官方 p3c 仓库当前公开的《Java 开发手册》黄山版（2022-02-03）为基线。核验日期为 2026-11-17。开发前按涉及主题查阅官方手册，保留强制、推荐、参考的原始等级。详见 [来源与选型](references/sources.md)。

先读项目规则、构建文件和现有代码，确认 JDK、Spring Boot、Spring Cloud、Maven/Gradle 及数据库版本。遵循对应版本的官方文档及兼容矩阵，优先使用项目 Wrapper 和 BOM。规范与项目实际约定冲突时记录差异，按用户要求和兼容性处理。不得借规范任务自动升级框架。

## 中文注释

新增与修改的人工注释使用简体中文。类、接口、公共方法的 Javadoc 说明职责、参数含义、返回值、异常与重要约束；解释复杂算法、事务边界、并发、幂等及业务取舍。修改行为时同步更新注释。
注释量按职责覆盖和可理解性验收。目前未核实阿里手册规定统一注释百分比，禁止把猜测的比例当成官方要求。简单访问器可依赖明确命名与已有生成工具，避免为了数量重复描述语句。
代码、注释、文件头和业务日志不得写入 Agent 名称、模型名称、AI 生成标记或虚构作者。已有版权与许可证声明依法保留。

## Spring 项目组织

Spring Boot 官方允许多种布局。默认采用按业务领域分包，领域内按职责组织 controller、service、repository/mapper、dto、config；已有合理结构优先沿用。启动类放在业务根包，避免默认包和过宽扫描。使用构造器注入，显式管理配置，禁止循环依赖。
Controller 处理协议、校验和响应，Service 承载业务及事务边界，Repository/Mapper 处理持久化；DTO 与持久化实体按边界分离。简单项目按实际职责设层，避免空壳接口或机械的一对一转发。
Spring Cloud 按业务边界拆服务，通过明确 API/事件契约通信；禁止跨服务直接修改对方数据库。对远程调用设置超时，按业务配置熔断与有限重试，重试写操作必须保证幂等。跨服务一致性按业务选择补偿、消息或事务方案，并覆盖部分失败与重复投递。

## 方法复用

实现前搜索已有方法、服务、转换器和框架能力，并检查调用者及行为契约。
出现可复用的相同业务能力时必须提取到职责所属组件，现有调用统一复用，避免重复校验、计算、转换和查询逻辑。先比较输入、异常、副作用、权限与事务语义，再合并。
仅表面相似但业务规则不同的代码应保留边界。公共组件应有稳定职责，避免把不同领域耦合进万能工具类。跨服务复用通过稳定契约或合适的基础库实现，避免共享业务实体导致发布耦合。
提取后核对全部调用路径、历史数据、空值、异常以及并发行为。

## 必备工程约定

- 接口明确参数校验、错误码、分页上限、权限和兼容策略；统一异常映射，记录可定位的上下文，避免吞异常及重复打印堆栈。
- 事务覆盖完整业务不变量，核对代理调用、自调用、回滚规则及异步边界；外部调用避免长时间占用数据库事务。
- 金额使用明确精度与舍入规则；时间明确时区；集合与可变共享状态注意线程安全；线程池设定容量和拒绝策略。
- SQL 使用参数化，检查索引、N+1 和大批量操作；结构变更使用版本化迁移并说明兼容和恢复方案。
- 凭据通过环境变量或项目配置系统注入；日志脱敏，权限在服务端校验，防止越权、注入及敏感数据泄露。
- 测试覆盖本次业务正常、边界、失败及涉及的并发/幂等路径。按变更风险选择单元、集成和契约测试，复用现有测试设施。
- 构建、格式、静态分析和依赖检查沿用项目 CI。按需采用 Checkstyle、PMD/P3C、SpotBugs 等工具，验证与当前 JDK 的兼容性；工具通过不能代替业务审查。

## Code Review 与交付

按 [审查规范](references/review.md) 检查需求、差异、调用者及验证证据，修复阻塞问题后复查。交付说明实现结果、执行过的检查和剩余验证缺口。
