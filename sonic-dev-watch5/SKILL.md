# sonic-dev-小米手表开发

把新需求推进到可构建、可安装、验证边界明确的 APK；优先复用本机证据，减少重新搜参数、找工具和试错。适用基线来自 2026-11-04/05 的国行 eSIM 实机，不把历史事实当作当前设备在线状态。

## 使用方法

在新聊天中调用 `$sonic-dev-小米手表开发`，并说明应用需求和目标工作目录。例如：“使用 $sonic-dev-小米手表开发，在 E:\Code\Sonic\watch5 开发一个倒计时应用，支持开始、暂停和重置。”技能提供已验证的设备基线、工程入口和排错流程。

若技能列表尚未刷新，直接读取本 `SKILL.md`。本技能不包含 Android SDK、JDK、业务源码或个人签名；资料不可达时按下面说明处理，不冒充已经完成工程检查。

## 接手与最少读取

资料根目录默认 `E:/Code/Sonic/watch5`。用户指定了其他工作目录时，在用户目录做开发，资料根只供参考，不擅自把项目移回默认目录。资料已迁移则使用实际根目录。

1. 服从目标目录的 `AGENTS.md`；在本工作区先读 `Agent.md` 的当前摘要和 `WATCH5_DEVELOPMENT.md`，再读目标应用最新 README/暂停记录。历史日志仅在追溯相关问题时展开。
2. 根据下表读取 `WATCH5_ENGINEERING_GUIDE.md` 的相关章节，不每轮加载所有项目历史。`WATCH5_AGENT_QUICKSTART.md` 是人工交接入口，已读本技能且了解流程时按需查阅；目录规则要求必读时遵守目录规则。
3. 首次开发、迁移机器或工具报错时运行本技能的 `scripts/preflight.ps1`；普通文档/布局小改无需重复检查整个环境。

```powershell
# $skillRoot 替换为实际加载的 SKILL.md 所在目录。
pwsh -NoProfile -File "$skillRoot/scripts/preflight.ps1" -Workspace 'E:/Code/Sonic/watch5' -Profile ui
# Profile 可选 ui / ble / port / docs，分别对应界面、蓝牙、移植、文档。
# 脚本仅检查本地文件，不调用 ADB、安装或联网。
```

结果只说明路径存在，不证明工具可执行、设备连接或 APK 能运行。缺少指定工具时先检查路径/脚本参数，只补缺项。缺少资料根时说明来源不可达，先利用下面的已知基线推进可做的工作；不能宣称已读取历史证据或执行构建。

## 已知基线及关键约束

- M2505W1、Android14/API34、480×480px、320dpi，名义全屏为 **240dp**；ABI 为 `armeabi-v7a, armeabi`。新设备/固件再核对，不因芯片支持64位就只提供arm64库。
- 已验证 Java + Activity/View/Canvas 与 SDK 命令行构建。Kotlin/Compose/Gradle 可按用户需求采用，但需单独验收；不默认 GMS、Wear Data Layer、OMS 或 Vela 可用。
- 固定图片优先 `res/drawable-nodpi` + `R.drawable`，aapt2 先生成 R 再编译。`assets/` 合法；检查最终 APK 资源和已安装版本，避免反复换图片格式掩盖文件打开错误。WebView 初始化通用报错不证明 provider 缺失。
- Canvas 的480设计坐标需统一缩放及触摸逆变换。圆屏中部放宽、上下收窄；字号、返回、翻页触控范围、键盘和大字号分别检查。Canvas 不会自动补齐字体缩放和 TalkBack 语义。
- 已有构建工具在 `tesla-watch/probe/.tools/`；JDK 默认 `D:/Scoop/apps/OracleJDK17/current`，均可重定位。保留现有包名/签名/钥匙数据；新应用独立包名。复制前检查个人默认配置，不复制 `.private/`、已生成个人 APK 或账号数据。
- ADB 每条设备命令明确 `-s` 目标；不随意重启共享服务或清数据。真实设备地址每次确认，不能复用历史 IP。启动后查看当前版本截图，黑屏、表盘、logo和别的应用都不能作为验收。
- BLE 权限、扫描、连接、发现、订阅、认证、发送、结果分阶段，均有取消和超时；拒绝旧回调。写入/队列成功不等于外设执行成功，未认证回复不等于配对完成。
- 无设备时完成代码、协议测试、构建和资源检查，列出待实测项。安装、启动、通信、账号授权、真实业务分别给证据。个人 VIN/密钥/令牌不进入通用文档，截图保护不为验收而关闭。

## 圆形桌面图标

- 后续新建或重绘的主入口和快捷入口统一使用圆形。国行 Watch 5 预装「设置」和「计时器」的 Launcher 图标均为 144dp × 144dp 的矢量资源，viewport 为 144 × 144。以此固定项目母版：圆心 (72,72)，半径 72，圆外透明，圆底贴画布四边。桌面排版决定显示直径；144 是资源规格。
- 固定主体图形居中于直径 96 的安全圆内。设计从有辨识度的鲜明主色开始，用同色系明暗过渡或一块局部高光表现底色层次，用高对比的简洁前景表达功能。每个图标以一主色、一辅助色为宜，细节按 48px 缩略图仍可辨认验收。
- `android:icon` 与 `android:roundIcon` 指向同一圆形主资源。快捷 Activity 单独设置 `android:icon`，复用主图标，在右上角叠加闪电圆章。144 母版上固定角标中心 (104,40)、直径 36，含描边的最外缘保持在底圆内。验收编译后入口资源、透明四角、48px 对照及真机桌面表现。

## 表冠、实体键与系统手势

- 前台表冠输入可先复用 `input-probe/README.md` 对应探针。国行实测收到 `SOURCE_ROTARY_ENCODER` 的 `ACTION_SCROLL`，从 `AXIS_SCROLL` 读取带方向的增量。另行记录实体键的 DOWN/UP；该次采样为零，具体按键是否向应用分发仍须逐键实测。
- 开发“手势直达应用功能”时，分别验收桌面图标数量、系统手势列表能否选到功能、绑定后实际到达的页面。当前固件实测中，单桌面入口配静态快捷方式，以及带独立名称和图标的 VIEW 深链，两种方案在手势列表里都只显示主应用。需要独立快捷操作且允许两个桌面图标时，使用下述双入口方案。
- 日志分别标记主入口启动、功能入口到达和按钮回调。普通 MAIN 启动无法区分手势和桌面点击；同一会话的多份导出按事件序号比较，累计值只取差值。证据见资料根下的 `docs/watch5/GESTURE_APK_COMPARISON_2026-11-06.md` 及探针 README。

## 手势启动快捷操作：同一个 APK 的两个入口

1. 在清单声明两个可导出的 Activity，各自带有 ACTION_MAIN 和 CATEGORY_LAUNCHER 的 intent-filter。主入口处理日常交互，快捷入口只处理已配置的动作。给两个 Activity 设置各自的桌面名称。快捷入口通过 Activity 级 android:icon 引用专用 drawable：以主图标为底，在右上角叠加高对比的小闪电徽标，为圆形裁切留边，并检查 48px 预览。
2. 主应用提供「设置 → 快捷操作」，显示当前选择，支持更换和关闭。按账号保存动作和稳定的目标 ID，与手动选择分开。快捷入口每次收到新的启动请求时重读配置，未设置、账号不匹配或目标失效时提示返回设置。配置页只保存选择。执行页沿用原有权限校验，每次有效启动最多发出一次请求，恢复页面或重绘时不重发。
3. 国行 Watch 5 的手势「打开应用」菜单会给两个条目显示同一个应用名。测试版给实际进入的页面加上可辨认的 A/B 字母和不同底色。在快捷操作关闭或使用模拟目标时，从表盘分别绑定并触发两项，按到达页面识别快捷入口。0.1.5 探针实测第一项进 B，第二项进 A；换设备、固件或版本后重新辨认。右上角闪电用来识别桌面快捷图标，菜单同名时仍以实际触发结果为准。
4. 用模拟目标验证设置、改选、关闭、结束进程后冷启动，以及切回现有任务时的实际前台页面。探针 0.1.6 验证改选后 B 冷启动能读取新目标；正式应用的业务回执另行验收。参见资料根下的 `input-probe/README.md` 和 `WATCH5_ENGINEERING_GUIDE.md`「主入口配置、手势入口执行」。

## 测试文件与日志导出

- 每次运行前先指定输出目录。每个应用选用固定的应用名称作为单层目录名，电脑和手表使用同名目录，如 `Download/logs/按键与手势测试/`。电脑以当前工作区为基准，仅把生成的测试文件放入 `download/test/<应用名称>/`，测试日志及应用导出日志的本地副本放入 `download/logs/<应用名称>/`。禁止将测试产物散落在工作区根目录、源码目录、桌面或其他目录。按用途归类：测试生成的 XML、截图、模拟输入 JSON 归 test；诊断 JSON、logcat、错误报告归 logs。测试源码和正式 APK 按工程结构管理。
- 手表侧对应系统共享下载目录的 `Download/test/<应用名称>/` 和 `Download/logs/<应用名称>/`。所有应用内手动或自动导出（含诊断值、错误报告）统一写入后者，即使格式为 JSON、XML 或图片。Android 使用系统下载集合和相对路径 `Environment.DIRECTORY_DOWNLOADS + "/logs/" + appFolder + "/"`，不硬编码挂载点。写入成功再提示实际文件名和位置；失败清理本次半成品并报告错误，不改投其他目录。
- 所有日志文件名以生成端本地时间 `yyyyMMdd-HHmmss` 开头，精确到秒，保留真实扩展名，如 `20261106-142443.json`。同秒重试或并发写入时独占创建并追加序号（如 `20261106-142443-02.json`），不得覆盖既有文件。日志正文按需记录应用、版本和带时区的时间，避免写入令牌、密钥等敏感数据。
- 交付前检查测试脚本、ADB 截图/拉取目标和应用导出路径，实际验证同秒连续导出可分别打开。只清理本次创建的临时文件。历史文件沿用原路径，迁移或删除须另有要求。

## 新建或更新 APK：签名与交付

- 所有手表 APK（含 debug、预览及测试包）在开始开发或打包时先完成下面的「本机签名备份与换机」配置；已有配置直接读取，不每轮重复询问。
- 新建应用先确定包名、版本号和长期使用的签名。沿用工程的私有签名存放方式并安排备份；交付目录、Git 和日志中不放密钥或口令。改已有应用（即使只换图标），先定位对应源码、构建脚本和旧 APK；确认脚本不会在原签名缺失时静默生成另一把钥匙。
- 判断能否覆盖，以手表当前版本或已核实来自该版本的旧 APK 为基准。用 `aapt dump badging` 核对新旧包名和 versionCode，用 `apksigner verify --verbose --print-certs` 核对签名验证结果和签名证书 SHA-256。常规同签更新要求包名不变、证书匹配、新版递增 versionCode。拿不到可靠基准时写「覆盖未核实」。APK 文件的 SHA-256 用于核对交付副本，不能用来判断签名是否相同。
- 找不到原签名时，保留旧包和数据。用户选择另出新签名版后，同包名但用全新密钥的 APK 单放在「新签名版-无法覆盖旧版/」，文件名也注明「无法覆盖旧版」。旧 APK 备份不能恢复签名私钥或应用数据，不自动卸载旧版。若仅要求保存图标，或缺源码且任务允许先交设计，交付圆形矢量 XML 和透明 PNG 预览，注明未生成新版 APK。
- 在用户指定的目录交付，每包按应用名和版本命名。核对最终包的图标和入口、签名、zipalign 对齐；复制后用 `Get-FileHash -Algorithm SHA256` 核对源包和交付副本。分别记录「已构建」「已导出」「已覆盖安装」「已启动」中有证据的状态；导出不等于安装，也不证明双入口手势绑定仍有效。

### 本机签名备份与换机

1. **先配置绝对路径。** 本机首次开发或打包前，向用户确认专用签名备份根目录，必须是当前电脑可访问的绝对路径，位于源码、Git、APK 交付和测试日志目录之外。路径按电脑单独配置，例如用户私有配置 `%LOCALAPPDATA%/Sonic/watch/signing.local.json` 中的 `backupRoot`；这是本机配置约定，不是 Skill 自带的自动功能。配置存在时复用；换电脑、路径失效或用户要求变更时重新指定，不把旧电脑盘符写死在通用 Skill。仅维护技能文档时无需配置真实目录。
2. **按包名存放。** 使用 `<backupRoot>/<applicationId>/`，保存实际签名的 `.keystore` 或 `.jks` 及恢复所需的签名配置。清单记录包名、密钥相对路径、alias、证书 SHA-256、密钥文件 SHA-256 和创建/校验时间。密码放密码管理器或加密凭据文件，清单只记读取方式；换机时同时恢复该读取方式。不把密码、密钥内容或含凭据的配置写入代码库、Skill、截图和日志。各应用保留自己的既有签名，不统一更换为一把新密钥。
3. **优先恢复固定密钥。** 开始打包先按包名查询备份；工程缺密钥时从已核对的备份读取，显式传入构建参数或安全恢复至工程私有签名目录。已有应用比对手表或可靠旧 APK 的证书，工程和备份冲突时停止签名并保留双方。若原有工程密钥匹配而备份尚未建立，先用它初始化备份。新应用只创建一次密钥，先完成备份再签名；已有应用无原密钥时不自动生成替代品，另出新签名版须遵守前文处理流程。
4. **每次打包都核验备份。** 在签名前备份本次实际使用的密钥及更新过的必要配置，核对副本文件哈希、alias 和证书指纹，验证密钥可用于签名。同内容备份已存在时重新校验即可；内容不同不直接覆盖，先查清原因并保留历史。备份不可读、不可写或校验失败时停止签名和交付，报告缺项；不得悄悄换目录或换密钥。构建脚本中将恢复、备份核验纳入签名前置步骤，关闭“文件不存在就自动生成密钥”的旧逻辑。
5. **换机流程。** 把备份完整迁入新电脑受保护的位置 → 配置新电脑的绝对 `backupRoot` → 按包名读取清单和凭据 → 核对旧 APK 的证书 → 用原密钥签名。源码目录或备份盘符变化不改变应用签名；找不到原备份时暂停需要原签名的打包。
6. **交付与记录。** 签名后再次核对 APK 证书与固定清单一致，将本次备份校验结果、版本和 APK 哈希记入 `download/logs/<应用名称>/yyyyMMdd-HHmmss-…`。交接文档记录“已配置/未配置”、非敏感的配置入口及恢复方法，不包含私钥和口令。首次接入既有工程时记录覆盖验证结果，不能把新建备份本身当作兼容旧版的证据。备份只在用户指定位置保存；上传 GitHub 仅限单独配置的加密备份或 Secrets，不提交原密钥。

## 执行与收尾

新应用先跑通标题、图片、按钮、返回的最小原生页，再扩展业务。已有应用按请求做最小相关修改；不重新设计用户已确认的界面。新应用用项目模板记录要求，随后验证构建/签名/对齐/资源；需要上机时依现有授权安装核对。

缺少设备不必停止独立开发；但无账号/实体卡/现场条件时不能制造配对或控车成功。历史用户要求“两个 agent”、固定 MAC 或个人默认值不自动推广成新任务要求。汇总资料也不恢复其他暂停任务。

交付写明 APK 路径、版本、构建结果、实际验证和未覆盖范围；可复用的新结论写回工程手册，专项证据留在应用目录。
