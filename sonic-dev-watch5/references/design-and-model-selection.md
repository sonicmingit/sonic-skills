# 需求设计、模型选型与开发委派

在手表应用开始代码实现前读取。先把设计写到目标工程的 docs/开发设计.md；工程有既定文档位置时沿用，不额外制造同内容文件。本文件是流程规范，不包含对某个模型的固定价格或性能保证。

## 设计交接需要写清的内容

按改动大小控制篇幅：小改可以在既有设计中补一段，但不能让开发者自行猜测行为。

| 内容 | 子 Agent 应获得的信息 |
|---|---|
| 需求与范围 | 用户目标、场景、输入输出、已确认行为、本轮不处理的部分、验收条件 |
| 页面与交互 | 圆屏布局或已选设计文件、状态、点击/滑动/返回/长按行为、文案、加载和错误提示；适用时明确 480px/240dp、图标与资源规范 |
| 开发方案 | 要修改的文件/模块、复用入口、数据结构、接口或协议字段、状态转换、生命周期、超时/取消及恢复处理 |
| 数据与安全 | 权限、持久化、升级兼容、固定签名备份配置、日志脱敏；子任务不传实际私钥、口令或令牌 |
| 依赖与证据 | 目标目录规则、最新专项记录、工具位置、已有验证、设备或账号可用条件；区分已证实与待验证假设 |
| 实施与验收 | 开发顺序、可执行的构建/验证命令、输出位置、通过条件、待实测项及触发停止的条件 |

已有功能保持用户确认的设计。用户已明确要求开发且需求足够时直接推进；仅在缺少会影响实现的信息时澄清，不把“先设计”变成额外的例行审批。

## 评估难度与选择成本

先看未知项、耦合和失败后果，再看改动量。根据平台当前提供的模型列表、能力说明和可确认的成本信息选型；可用名称、价格及推理档位会变化，不从本文件推断固定排名。不掌握价格时记录相对成本依据，不编造金额。

| 难度 | 常见任务 | 选择原则 |
|---|---|---|
| 简单、边界清晰 | 按已定稿设计换图标/文案、局部布局、确定性的小修复 | 优先可用的经济型编码模型与较低推理档位，交给一个子 Agent 完成 |
| 中等、可复用方案 | 多页面状态、配置持久化、按已验证接口增加功能、明确复现的生命周期修复 | 选能处理相关上下文和调试的常规编码模型；经济型足够时继续用经济型 |
| 复杂、未知较多或失败后果较大 | 新 BLE 认证或协议、JNI/跨进程问题、难复现崩溃、涉及既有钥匙或数据兼容的改造 | 先缩小到能验证假设的任务；确需较强模型时初选并说明理由，不用最低档反复盲试，也不把全项目一律交给最高档 |

选型记录放在开发设计中，至少包含：

- 任务和当前难度判断、关键风险与未知项。
- 当前可用的候选模型、最终模型的实际标识符和推理档位、选择理由及成本依据。
- 主 Agent 与实施子 Agent 的职责、允许修改的文件范围。
- 验证方式、回交内容和需要重新评估选型的条件。

只有同样能满足验收的候选才比较成本，同时考虑上下文传递、重复劳动和返工；不能以少做必要验证换取表面便宜。默认一个实施子 Agent；只有可独立工作且确能减少总成本或耗时的部分才考虑增加，不无理由并行或层层委派。

## 委派方式

在支持模型选择的环境中显式指定已选模型和推理档位。若当前工具指定不同模型时要求使用 fork_turns=none，则使用该方式并附上必要文档路径，不为继承历史对话而放弃选型。工具参数以当前环境声明为准；不能通过文字要求子 Agent “假装切换”。

任务说明应包括：目标、开发设计路径、目标 AGENTS/README、相关源码与证据、模型决策、允许修改的文件、构建与验收方式、输出路径和停止条件。让子 Agent 先读这些材料，仅补充缺失侦测。不得复制全套业务凭据、签名私钥或无关历史。

子 Agent 回交：实际变更文件、实现行为、构建/测试证据、APK/日志位置、未验证项及阻塞。主 Agent 检查关键差异和证据，重点复核签名、数据兼容及外设控制等高后果部分；已有检查通过且没有新疑点时不重复整套测试或重新实现。

## 遇到问题与升级

卡住时先定位原因。命令路径、权限、离线设备、缺少密码或需求含糊等，应补足对应条件；代码或推理问题则保留最小复现、相关错误和已尝试的有依据修正。没有新证据时不反复盲试、不不断追加 Agent。

确需升级到更高成本模型或推理档位时，提交简短建议：当前模型/档位、未解决的问题、证据与尝试、目标模型/档位、预期帮助以及本次升级范围。询问用户是否同意；等待期间可继续不依赖升级的工作，不把等待或无回复当作同意。

用户同意后把既有设计、变更和失败证据交给升级后的实施 Agent，保留现有成果，按批准范围解决问题；不要从零重做整个应用。更新选型记录，交付时说明实际采用的模型及仍待验证的边界。
