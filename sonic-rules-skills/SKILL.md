# sonic-rules-技能创建规范

## 适用范围与使用方法

为 Sonic 新建或更新自定义技能前，先读取本文件，再读取当前环境提供的技能创建指南。适用于任何项目或工作目录中的技能创建任务，也适用于本规范自身的更新。

可以直接说：“按照 sonic-rules-技能创建规范，帮我创建一个用于……的技能。”旧称“sonic-技能创建规范”在自然语言中仍指本技能；安装路径和显式调用使用新名称。执行已有技能所支持的业务任务时，无需重复执行本规范。

在技能维护上下文中，用户说“推送一下我的更新”“推送我的 Skill 更新”“把我创建的技能更新推送到 GitHub”等同类表达时，执行 [本机检查与同步流程](references/本机检查与同步.md)。优先处理当前对话中创建或修改的技能，以及用户明确指定的技能，先汇入 OneDrive 对应目录、补齐中文更新日志，再提交并推送 GitHub；不要求用户使用固定句式。当前上下文不能确定具体技能时，扫描默认目录，推送可确认属于用户的本机新增或更新，跳过冲突项目。用户明确说“全部”时按其指定范围扫描。普通代码项目中的“推送更新”不能仅凭该短语触发本技能。

也可以说：“检测我创建的 Skill”或“检测我创建的技能”。“检查我创建的技能”和原有的“检查本机 sonic- 技能，有更新就同步到 GitHub”同样有效，不要求大小写或空格完全一致。此时读取 [本机检查与同步流程](references/本机检查与同步.md)，扫描默认目录、比较内容并按既定同步要求发布可确认的本地更新。若用户明确说“只检查”或“只检测，不同步”，仅报告差异，不改动文件或推送。

用户说“查看一下技能有没有更新”“检查技能有没有更新”“从 GitHub 更新技能”或指定某个技能查看更新时，执行 [GitHub 更新到本机流程](references/GitHub更新到本机.md)：查询对应远端技能，有可确认更新则下载至 OneDrive，再更新当前 Agent 可读取的技能目录。用户已授权这类调用完成检查与安装，无须在发现更新后重复询问相同授权。没有指定技能时，检查当前 Agent 已安装且能对应本仓库的自建技能，不将整个远端仓库的未安装技能自动装入本机。

按用户表达的同步方向选择流程；明确说“只查看”“只检查，不更新”或“不修改文件”时只读。“不推送 GitHub”不禁止明确要求的下载更新。下载模式不顺带上传本机改动。

## 命名与中文要求

- 统一格式：目录名为 `sonic-类别-英文用途`；技能名称为 `sonic-类别-中文用途`。`sonic` 和类别均为小写，连字符使用半角 `-`。
- 目录名只使用小写英文字母、数字和连字符，简短表达用途；例如 `sonic-dev-watch5`。本规范的目录名为 `sonic-rules-skills`。
- 技能本身的名称（`SKILL.md` 的 `name`）、文档标题和 `agents/openai.yaml` 的 `display_name` 使用相同中文名称；例如 `sonic-dev-小米手表开发`。目录名和中文名称的类别必须一致，后缀可以不同。本规范名称为 `sonic-rules-技能创建规范`。

| 类别 | 适用范围 | 英文目录示例 | 中文名称示例 |
|---|---|---|---|
| `rules` | 规范、约定、创建与维护流程 | `sonic-rules-skills` | `sonic-rules-技能创建规范` |
| `dev` | 应用、固件、脚本或集成开发，移植与调试 | `sonic-dev-watch5` | `sonic-dev-小米手表开发` |
| `use` | 通用工具、外部平台和设备的直接使用 | `sonic-use-gemini-image` | `sonic-use-Gemini图片生成` |
| `svc` | 通过自部署服务完成业务操作 | `sonic-svc-spoolman` | `sonic-svc-耗材管理` |
| `ops` | 服务部署、升级、备份、恢复、运行监测与排错 | `sonic-ops-spoolman` | `sonic-ops-耗材服务运维` |

- 先按主要目的选一个类别，再确定用途名称，不叠加多个类别。同一服务可按实际需要分别提供 `svc` 业务技能和 `ops` 运维技能，例如记录耗材属于 `svc`，升级 Spoolman 和恢复数据库属于 `ops`；不要仅为了分类新增技能。
- `use` 与 `svc` 按实际依赖区分：通用工具、设备或外部平台操作用 `use`，面向用户自行部署服务的业务操作用 `svc`。开发 API 集成代码属于 `dev`；使用现成 API 完成业务不因此变成 `dev`。
- 服务器独有不是类别。服务器名称、部署方式、运行环境和访问前提写入技能说明，不把机器路径、地址或凭据编码进名称。`ops` 关注运行维护，`rules` 关注规范流程；本规范虽包含同步操作，仍归 `rules`。
- `description`、说明、使用方法、示例解释、参考文档及面向用户的提示均使用简体中文；目录名称使用英文不改变文档内容的中文要求。
- 必须保持原样的文件名、配置键、代码标识符、命令、网址和产品专名无需翻译，例如 `SKILL.md`、`name`、`description`、`GitHub`。
- 源文件统一使用 UTF-8。代码注释及可控的用户提示优先使用中文。
- 若目标平台确实限制内部标识符只能使用小写英文，则使用与目录相同的 `sonic-类别-英文用途` 技术标识符，并保留 `sonic-类别-中文用途` 作为显示名称和文档标题；说明兼容性例外，不静默把用户名称改成英文。
- 现有技能不因本规范自动批量改名；用户要求迁移时再同步调整调用引用和安装入口。第三方或系统技能不纳入批量改写范围。
- 获授权迁移旧技能时，先建立旧目录和名称到新目录和名称的映射，核对重名冲突，再更新目录、正文名称、界面元数据、引用路径、安装链接及更新日志；GitHub 保留改名历史，不发布新旧两个重复技能。更新全局入口后验证可读。不得将“整理总规则”自动扩展成所有技能的批量迁移。

## 文件存放与内容

- 自定义技能的默认维护源目录为当前 OneDrive 根目录下的 `AI/skills/sonic`，每个技能独立一个子目录。按 [本机检查与同步流程](references/本机检查与同步.md) 中的定位规则，从当前进程的 `OneDrive`、`OneDriveConsumer`、`OneDriveCommercial` 环境变量解析，不能把某台电脑的盘符作为通用路径。本机当前解析结果为 `E:\Sonic\OneDrive\AI\skills\sonic`，仅作为示例。
- 仓库采用扁平布局：`<OneDrive>/AI/skills/sonic/sonic-类别-英文用途/SKILL.md`。类别通过名称前缀表达，不额外嵌套 `dev/`、`svc/` 等分类目录，以保持现有技能发现和同步流程可用。
- 每个技能至少包含 `SKILL.md`，明确用途、触发条件、使用方法以及完成任务所必需的步骤。仅在有实际需要时添加脚本、参考资料或素材。
- 需要界面元数据时使用 `agents/openai.yaml`，其中显示名称、简短说明、默认提示均使用中文，名称遵循 `sonic-类别-中文用途` 格式；默认提示中的显式调用名称与技能的实际标识符一致。
- 需要全局发现时，将技能安装或链接到当前环境的用户技能目录，优先链接维护源，避免维护两个内容分叉的副本。

## 更新日志

- 每个自建技能必须在其目录中维护 `CHANGELOG.md`，使用中文记录；每次实际修改技能正文、脚本、参考资料、配置或素材，都在同一次提交中增加对应日志。新技能记录首次创建。
- 条目使用北京时间的日期（`YYYY-MM-DD`），最新记录在前；同一天有多次独立更新时可增加时间或小标题。写明新增、修改或修复的实际内容，以及必要的兼容性影响。
- 已有技能首次纳入规则且缺少日志时，记录“首次纳入版本管理”和本次可核实的变更，不编造过去的日期、版本或历史。
- 扫描、验证或重复同步没有产生内容变更时，不制造日志或空提交。日志只记录已完成的内容，不预先宣称推送成功，也不因为补写日志自身而无限追加日志。
- Git 提交说明不能代替每个技能自己的更新日志。
- 从 GitHub 下载或安装既有版本时保留其原有 `CHANGELOG.md`，不为单纯同步文件额外制造技能变更日志或回推提交。只有实际修改技能内容时才新增日志。

## 更新与 GitHub 同步

目标仓库：`https://github.com/sonicmingit/sonic-skills.git`。

用户已要求后续自定义技能更新及时同步；每次完成创建或修改并通过检查后，在同一任务内提交并推送本次相关变更。用户明确要求暂不推送时，以当次要求为准。这是任务结束时的同步流程，不代表存在后台文件监听服务。

1. 先检查维护源目录是否为 Git 仓库，核对远程地址、当前分支、未提交变更和远端历史。首次连接时保留现有本地技能与远端内容；必要时先在独立目录检出远端，再合并本次文件，不能用远端覆盖本地目录。
2. 检查本次文件和差异，确认每个发生更新的技能均已补充 `CHANGELOG.md`，运行可用的技能校验及必要的脚本验证。若通用校验器只因中文名称报错，区分校验器约定与目标平台实际限制，并明确记录结果；其余格式和内容问题仍需修复。
3. 只暂存本次任务涉及的文件，使用中文提交说明。不要将凭据、令牌、私人运行数据、缓存、日志或无关改动带入提交。
4. 推送到核实后的目标分支，不强制推送、不丢弃用户修改。远端领先时先检查差异再整合；无法安全解决的冲突停止推送并说明。
5. 核对远端目标分支的提交与本次本地提交一致后，才报告“已同步”，并给出提交号或链接。网络、身份验证或权限受阻时保留本地成果，报告“尚未同步”及具体原因，不无限重试。

## 交付检查

确认类别选择、英文目录与中文名称中的分类前缀一致、中文内容、更新日志、源目录、引用路径和必要验证结果。交付时说明类别、技能位置、调用方式以及 GitHub 同步状态；本机检查还需报告扫描目录、技能数量、同步和跳过的项目及原因。
