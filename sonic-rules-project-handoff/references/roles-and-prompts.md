# 分工与调用提示词

## 主模型先完成可执行设计

简单任务直接执行并验证。复杂任务先读取实际代码、项目规则和现有计划，在已有 `PLAN.md` 或等效文件中完成以下内容，再派发实现任务。

1. 将用户目标映射到可观察的验收条件，列出本次范围、不做范围及需要保留的现有行为。
2. 标明当前实现和关键证据，区分已知事实、假设和阻碍。影响架构的未知项先做有界探索，探索任务应有具体问题和结束条件，得到结果后再确定实现方案。
3. 明确模块边界、输入输出、接口字段、错误行为、数据兼容性和必要的回退办法。只细化会影响实施或验收的设计，不预写全部代码。
4. 按可独立验收的交付物拆任务，画出或列出依赖关系，识别关键路径。每项需改变的行为都明确实现负责人和验收方式，已有行为可通过核验确认，无须重复实现。检查或研究任务以可核验结论为交付物，避免遗漏与重复。
5. 为每项任务填写下方任务卡，按依赖安排批次，并选出合适模型。共享接口先约定，前置任务完成且验收后才释放依赖任务。

主模型保留跨模块取舍、接口变更、冲突处理和最终验收职责。常规实现细节由执行者决定，只有重要且无法从现场推断的产品取舍需要用户决定。已有设计足够时补缺即可，不重写整份计划。

## 可直接派发的任务卡

每个实际派发的任务提供以下信息，可作为计划中的小节，不另造重复角色文件。对短小任务可合并字段，已在计划明确的内容引用即可，不逐项重复抄写。

- **编号、目标与交付物**：明确要改变什么行为，产出哪些文件或结论。
- **前置依赖与输入**：依赖任务编号、已确认接口、项目路径、适用规则、相关文件和当前版本。共享已有工作区时指出需保留的未提交改动。
- **修改所有权与边界**：允许修改的文件/目录、只读区域、不做事项。公共文件和接口指定唯一写入者，其他执行者只提交建议。
- **实施要求**：关键设计约束、输入输出、兼容性及错误处理，不要求执行者重新猜测主模型已经作出的决策。
- **验收条件与检查**：可观察的成功标准、要运行的检查及范围、必要的失败路径。命令未经核实则明确标注。
- **模型选择**：拟请求的模型标识、可配置时的推理档位、选择理由及能力限制。派发后仅按宿主返回的信息记录实际模型，宿主未暴露时写“继承默认 / 实际型号未核验”，不把请求参数或推测当作实际结果。只填写宿主实际允许的参数。
- **停止与升级条件**：缺少关键输入、需要改接口或越过写入边界、遇到权限限制或重复失败时，带证据报告主模型。
- **回报格式**：改动与文件、验证命令及结果、未验证项、阻碍和对其他任务的影响。无须复制大量日志。

派发时提供足够且相关的上下文，不假定子 Agent 能看到全部聊天。明确它是否可以写文件及运行哪些操作。主模型统一更新共享计划和交接卡，避免多个执行者同时改写记录。

## 按任务选择模型

派发前必须读取[子 Agent 模型与思考等级选择](model-routing.md)，逐任务明确模型和思考等级。默认优先评估 Luna、Sol、Terra，禁止因为主模型是 Astra 就批量继承相同模型或思考档位。该文档包含任务分配表、工具参数、失败升级通知和官方依据。

任务卡记录初始模型/档位、选择理由及已授权升级范围。未获得升级授权时，能力不足先报告建议并等待该项决定，其余独立任务继续。权限、环境或输入缺失不得通过换模型绕过。

## 并发调度与文件冲突

- 整个任务树同时运行的子 Agent 最多 3 个，主模型不计入，验收和探索同样占名额。用户或宿主上限更低时采用更低值。
- 子 Agent 默认不得继续派生代理，主模型统一维护活动任务、依赖和写入所有权。区分活动任务数和宿主保留的代理实例数。运行中、等待工具返回及状态不明的任务均保留并发名额，任务已确认结束且不再写入后才释放。空闲实例能否复用或是否仍占宿主容量，以工具实际限制为准。恢复旧代理前重新计数，不启动同一任务的重复执行者。
- 存在未满足依赖、重叠写入或接口尚未稳定的任务串行。多个任务只读同一文件不构成写入冲突。目录不同不代表可独立并行，还须检查共享的构建输出、测试数据库、端口等资源，必要时隔离或串行运行。
- 在共享工作区直接协作时严格分配写入范围，不回退其他人的修改。已有隔离工作区可按项目惯例使用，整合时由主模型处理冲突。
- 等待子任务时主模型可做不冲突的准备、审查已完成任务或补充验证。不要重复实现已委派任务。
- 执行者报告完成后先记为“待验收”，主模型检查产物与证据后才标记“通过”和释放后继任务。用“待开始、执行中、待验收、通过、阻塞、取消”区分状态，失败回到受影响任务修复，不自动回滚代码或删除产物。
- 方案或接口变化时，主模型定位受影响的任务和验收项，暂停相关写入，更新任务卡并通知执行者确认后续接。旧接口下的产物和测试不能直接沿用为新方案的通过证据，不受影响的工作继续。

例如新增带配置页的 API 功能，主模型先确定请求/响应、错误约定和配置存储方式。接口稳定后，可并行安排 API 实现、配置页实现、独立测试用例准备三个任务，各自拥有不同文件。需要运行完整接口的测试等待实现完成，主模型最后执行集成验收。若前端仍依赖未知接口，则先串行确定接口，不提前启动三个实现代理。

## 验收与交接

主模型核对每项需求对应的交付物、实际差异和验证证据，再运行覆盖跨任务接口与关键用户路径的必要检查。验证结果关联当时的提交或未提交差异及执行环境，后续修改影响被测行为时只重跑受影响检查。最终验收使用稳定的整合产物，避免其他代理边改边测导致结果失效。独立验收提示词可用下例。

“按计划的验收标准检查真实代码差异和测试输出，不依赖实现者的完成声明。报告阻塞问题、未覆盖验证及非阻塞建议，附对应文件或证据。暂不修改业务代码。”

验收发现问题后派回具体任务，修复后重跑受影响检查。没有独立代理时明确是自查。交接记录保留任务编号、实际模型、已完成与运行中状态、验证证据、未解决依赖和第一条下一步。跨会话续接先核验现场，不假定旧代理仍可用。

## 调用示例

- 初始化并继续：“使用 $sonic-rules-项目交接与分工 检查此项目已有规则、计划和交接文件，保留现有内容并补齐缺项。本次要实现……，初始化后继续实施和验证。”
- 仅建立流程：“仅初始化，不改业务代码。”
- 设计分工：“主模型先完成方案、接口和任务卡，再按各任务复杂度选择性价比合适的可用模型，最多同时运行 3 个子 Agent，由主模型整合验收。”
- 续接：“读取现有记录，核对代码版本、未提交改动和环境，从下一步继续，不重复已验证且仍适用的工作，不覆盖未知改动。”
- 收尾：“保存实际结果、测试和未验证项、未提交改动及下一步，不启动新的长任务，不自动推送，简短说明结果和剩余事项。”
