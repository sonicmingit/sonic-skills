# sonic-rules-项目交接与分工

用少量真实、可核验的项目文件减少用户搬运上下文和反复选择下一步的负担。默认用简体中文维护说明和示例。项目已有文档语言约定时，沿用项目约定。

调用示例：“使用 $sonic-rules-项目交接与分工 补齐这个项目的交接记录，然后继续完成本次已授权的任务。”

## 宿主与分工适用范围

项目规则、计划、交接与续接可用于各宿主。第 3 节及其参考资料中的自动分工、子 Agent 调度和按任务选模仅适用于 Codex，以当前宿主能力为准。其他宿主或宿主无法确认时，分工有实际收益则先提出建议，请用户选择当前模型继续或采用该方案。收到明确选择前，由当前模型推进已授权且无需分工的工作，委派和模型切换等待确认。

## 1. 先定位项目与请求范围

1. 从当前工作目录及用户给定路径确定项目。存在多个不相关项目且无法确定目标时，只问项目选择这一必要问题。
2. 先读取适用的上级及项目 `AGENTS.md`、子目录规则、README 和已有开发/交接文档；遵守适用指令及确认要求。本 Skill 不赋予额外权限。
3. 核对实际文件、Git 分支/提交（若存在）、工作区改动、工具版本及所需服务。没有 Git 时写“非 Git 项目”，不要擅自初始化 Git。
4. 将用户本次目的归为：初始化、计划、执行、验收、续接或收尾。只要求检查或评审时只报告发现，不因本技能补建项目文件或修改业务代码。只要求计划时不实施方案，只要求初始化时不要修改业务代码；用户已经给出实现目标时，完成必要初始化后继续实现，不要停在生成文件上。
5. 不扫描无关目录，不读取凭据值；可检查配置项是否存在，输出仅记录“已配置/缺失/未核验”。

## 2. 复用文件，再补齐最小结构

默认分工：
- `AGENTS.md`：稳定规则、目录和技术约定、已核验的开发/测试命令、工作边界。
- `PLAN.md`：本次复杂任务的范围、取舍、步骤、依赖与验收标准。简单任务省略，在交接卡写目标和验收条件即可。
- `HANDOFF.md`：最新实际状态、验证证据、未提交改动、阻碍和下一步。

按需参考 [项目规则模板](assets/AGENTS.template.md)、[任务计划模板](assets/PLAN.template.md)和[交接记录模板](assets/HANDOFF.template.md)，根据实际项目填写可核验的信息。

**保护已有内容：**
- 已有等效文档时沿用其路径、格式和单一事实来源，勿另造一套平行文件；在交接卡注明实际文档路径。
- 保留原文和用户编辑。只补必要缺项，不用模板替换整个已有文件。已有规则冲突时先核对适用范围，重大冲突再询问。
- 在已有 `AGENTS.md` 添加流程要求时，用清晰独立的小节；重复调用时更新该小节而非重复追加。已有等效规则则不追加。
- 保留尚未结束的其他任务计划，不覆盖为新任务；按项目已有惯例使用独立任务文件，并在交接卡索引活动任务。
- 默认只维护三类文档，不额外生成角色文件、日志副本、看板或新平台。特殊项目按需增补，说明用途。
- 长期规则只记录已知事实和明确约定，未知命令标为待核验。不要把本次推测或临时方案升级为永久规则。

## 3. 选择适当流程并继续工作

### 简单改动

直接执行 → 针对性测试/检查 → 更新交接卡。不要为了流程而启用三个代理或编写长计划。

### 复杂改动

主模型设计 → 明确任务卡与依赖 → 按任务选模 → 分批执行 → 主模型整合验收 → 更新交接卡。

- **主模型负责设计与调度**：先核查现状，将目标转成可观察的验收条件，明确方案、接口/数据约定、风险和回退条件。先解决影响多个任务的设计问题，再派发边界明确的任务。按[分工与调用提示词](references/roles-and-prompts.md)建立任务卡、选择模型并管理执行批次，不能只给子 Agent 一个模糊目标。
- **执行者负责限定任务**：只修改任务卡指定范围，遵守接口约定，提交实际改动、验证证据和未解决事项。设计前提失效时报告主模型，不能自行扩大范围或修改其他任务负责的文件。
- **验收者检查实际产物**：直接检查需求、代码差异和测试输出，区分阻塞缺陷、验证缺口和非阻塞建议。主模型对跨任务集成和最终交付负责，不能把各子任务分别通过当作整体通过。

**并发上限为 3 个子 Agent，主模型不计入。** 整个任务树共同遵守此上限，包括执行、探索和验收代理。子 Agent 默认不得再创建子 Agent，新增或替换均由主模型统一调度。任务总数可以超过 3 个，按依赖分批执行。存在写入冲突或未满足的前置依赖时串行，只在确有收益时并行，不为了填满名额拆任务。

**成本优先选模**：每次委派前读取[模型与思考等级选择](references/model-routing.md)。简单重复工作优先 Luna，范围明确的修复、视觉和界面任务考虑 Terra，常规实现与复杂技术任务优先 Sol。主模型继续设计与整合，Astra 子 Agent 仅在明确必要时使用，禁止批量继承当前主模型。逐任务显式选择 `model` 与 `reasoning_effort`，核对上下文继承是否阻止模型覆盖。当前不支持独立选模时说明限制，不把继承主模型伪装成成本优化。

失败先排查输入和环境。需要提高模型能力或思考等级时，先报告失败证据与升级建议，按已有授权执行；未授权升级则等待用户决定，只暂停受影响任务。没有子 Agent 工具时采用串行流程并说明能力限制。

角色是职责，不强制三个模型或三个会话。复杂分工前读取上述参考流程。可用且合适时安排独立验收，无独立代理时明确为自查。不要承诺工具未支持的自动切换模型、准确预测额度、定时续跑或后台监控。本流程不增加用户授权或绕过宿主限制。

## 4. 每个可验证阶段保存交接

在每个小批次完成、重要方案变化、遇到阻塞、用户要求暂停/收尾时更新交接卡，不等额度耗尽。用户要求暂停或停止时，主模型停止派发，通过可用工具通知或中断活动子 Agent，并核实其实际状态和遗留命令。无法停止的进程应明确记录，不能只写交接卡便声称已全部停止。及时保存已授权的工作文件，但不要因“交接”擅自提交、推送、发布或部署。

写明：
- 目标与当前阶段；核验时间含时区。
- 代码版本/工作区实际改动与环境；注意 HEAD 不能代表未提交改动。
- 哪些完成，哪些只计划了，哪些仍在运行。
- 验证命令、执行位置、实际结果与适用范围；区分通过、失败、未运行、被阻塞。不能以局部测试冒充全量验证。
- 已尝试但失败的方法和结论，避免下次重复。
- 下一步的第一条具体动作；用户只需决定尚未解决的关键选择。

长日志保留在合适位置，交接卡仅记录脱敏摘要与可用引用。不要写密码、Token、密钥、完整 `.env`、带凭据的 URL 或无关个人信息。文档将进入公开/共享仓库时，也避免复制私有地址和日志；使用占位描述或安全的本地配置引用。

## 5. 续接与换电脑

先读规则、计划和交接，再核对现场，最后继续。若文档与现场冲突，以核验结果修正文档；遇到未知来源改动，保留并判断是否妨碍本次工作，必要时只询问冲突部分。

交接文件不等于环境迁移。换电脑时检查代码版本、未提交/未跟踪文件、忽略的配置与数据、依赖及运行服务是否已到位。进程 PID、绝对路径和运行会话通常不能跨电脑复用。仅在用户授权的方式和范围内同步文件；不复制秘密到交接卡或擅自推送工作区。

恢复后先处理一个具体下一步，不重复读取无关历史或重做已有证据支持且仍适用的工作。

## 6. 高风险项目与完成标准

数据迁移、NAS 整理或恢复：单独记录清单生成、复制启动、复制完成、内容校验、原件是否删除。退出码成功不等于内容已校验。保留原件；删除、生产发布、安全设置和数据库破坏性变更遵守当前授权及确认要求。

代码完成、测试通过、部署完成、用户目标达成是不同结论。只有证据支持才升级状态。任务未完成且可继续时继续执行，不把“文件已建立”当作整个任务完成。

收尾向用户简短汇报：
1. 做成了什么。
2. 如何验证，哪些还没验证。
3. 下一步或需要用户决定的事项（无则省略）。

仅安装本 Skill 不会自动为所有未来项目创建文件。项目开始时显式调用，或由宿主根据描述匹配；每个项目第一次执行后，其项目规则可持续要求维护交接文件。
